# Подключение собственного станка

Числовой `ParameterRecipe` находится в core. `ConfiguredItemRecipe`, `ProductionRecipe`, `ItemParameterStorage` и `ItemInputFilter` — в Fabric-модуле. Основной Fabric JAR уже включает core; отдельно класть core JAR в `mods` не нужно.

В Java-проекте другого Fabric-мода используйте `modImplementation` для опубликованного `dev.itemparams:item-parameters-fabric:<version>` или локального собранного JAR. Публичный удалённый Maven-репозиторий пока не настроен. При распространении укажите зависимость `itemparams` в metadata своего мода.

## Подготовка линии

1. Загрузить проверенный каталог `ItemCatalogLoader.load(path)` либо получить установленный snapshot через `ConfiguredItemParameters`.
2. Выбрать `ConfiguredItemRecipe` по ID. Он уже содержит скомпилированный числовой рецепт.
3. Для каждой входной роли создать `ItemInputFilter.of(item, schema)`.
4. При первоначальной настройке передать входные стеки по именам ролей в `recipe.execute(Map<String, ItemStack>)`.
5. После полного успеха сохранить независимые образцы допустимых входов и копию рассчитанного выхода. `ItemInputFilter.lock(stack)` фиксирует один числовой профиль.

Сам вычислитель не отвечает за игровой инвентарь. Нужные Item ID, числовой профиль, количество, доступ к слотам и переход производства в другое состояние контролирует механизм.

## Обычная операция

```text
Проверить допустимые предметы и количество
→ проверить свободное место под сохранённый выход
→ атомарно израсходовать входы и вставить копию сохранённого результата
```

Формулы заново не вызываются. При загрузке мира восстанавливаются подтверждённые образцы и готовый выход. Перенастройка явно заменяет сохранённую пару; две одинаковые машины могут иметь разные рецепты или настройки.

Один `ParameterRecipe.Workspace` помнит последнюю комбинацию в памяти, но **не заменяет** сохраняемую в мире пару вход/выход и правила допуска механизма.

## Все пути вставки

Используйте одинаковое правило `filter.matches(stack)` для ручной вставки, Shift-click, воронок/сторон и API автоматизации. Проверки только перед завершением операции недостаточно: неподходящий стек не должен приниматься в слот. В demo это показано в `ProcessorScreenHandler`, `ProcessorBlockEntity` и связанных проверках.

Проверку вместимости выхода и расходование выполняйте на серверном потоке по текущему состоянию слотов. Ошибка настройки/формулы или полный выход не должны расходовать вход. Возвращаемые образцы и ItemStack не должны давать вызывающему коду изменять сохранённый эталон по общей ссылке.

## Владельцы данных

`ItemParameterStorage.read/write/edit` работают с ItemStack. `ParameterNbtStorage` позволяет использовать то же представление параметров в собственном NBT сущности/блок-сущности. Сохранение владельца, `markDirty`, синхронизация и миграции данных остаются задачей интеграции.

Внутри одного стека значения однородны. Предметы с разными NBT-параметрами не объединяются в один обычный стак. Новые сочетания чисел не требуют регистрации новых Item ID или новых рецептов.

## Учебный станок

Установите основной и demo JAR одинаковой версии. Demo использует тот же серверный каталог, четыре входных слота и один выход. При пустом каталоге он устанавливает учебные определения; пользовательский непустой каталог не заменяет.

Это пример интеграции, а не универсальный патч ванильной печи или Industrial-механизмов. Для разработки: `./gradlew :fabric:runDemoClient` или `:fabric:runDemoServer`. Принятие Minecraft EULA и серверные файлы относятся к локальному запуску и в Git не добавляются.
